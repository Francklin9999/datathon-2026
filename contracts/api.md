# contracts/api.md — HTTP API v1

Base URL: `{API_BASE}/v1`. Local default: `http://localhost:8000/v1`. On AWS the base is the API Gateway URL published by the CDK stack (`infra/SPEC.md`).

All types named here are defined in `contracts/schemas.md`. All codes are in `contracts/catalog.md`.

## 0. Common rules

### Headers

| Header | Direction | Required | Meaning |
|---|---|---|---|
| `X-Aplomb-Session` | request | yes, except `/health` and `/meta` | `SessionId` generated by the browser and kept in local storage (A-20). Missing → `422 validation_error`. |
| `Accept-Language` | request | no | `en` or `fr`. Only used when a body has no `lang` field. Default `en`. |
| `Content-Type` | request | on bodies | `application/json` |
| `X-Request-Id` | response | always | Echoed in `ApiError.error.requestId` and in logs |
| `X-Aplomb-Data-Version` | response | always | `DataVersion` used to answer |

### Errors

Every non-2xx response has the body `ApiError`:

```json
{ "error": { "code": "validation_error", "message": "sizePct must be greater than 0", "details": { "fields": [ { "path": "move.sizePct", "problem": "must be > 0" } ] }, "requestId": "req_01JCM9Z3" } }
```

### Other rules

- **CORS**: the API allows the CloudFront origin and `http://localhost:3000`.
- **Idempotency**: `POST /runs` accepts an optional `Idempotency-Key` header, scoped to session; the same key and request body within 10 minutes return the same `runId`. Reusing a key with a different body returns `409 conflict`.
- **Rate limit**: 30 requests per second per session; 6 run creations per minute per session. Exceeding → `429 rate_limited`.
- **No endpoint places, simulates or routes an order.** A request that asks for one is refused with `400 forbidden_action` (EF-16, brief p.17).
- **Latency targets**: read endpoints < 500 ms; `POST /check` < 1,500 ms; `POST /requests/parse` < 10 s; run creation < 500 ms.
- **Tiers**: each endpoint is marked P0 or P1. P1 endpoints return `501 feature_disabled` when their feature flag is off.

## 2. Universe

### 2.1 GET `/assets` — P0

Query: `q` (matches ticker or name, case-insensitive), `assetClass`, `theme`, `tier`, `limit` (default 50, max 500), `cursor`.

`200` → `{ "items": Asset[], "nextCursor": string | null, "total": number }`

### 2.2 GET `/assets/{ticker}` — P0

`200` → `Asset`. `404 not_found` when the ticker is not in the snapshot (the client may then call 2.3).

### 2.3 POST `/assets/{ticker}/fetch` — P1 (`on_demand_tickers`)

Fetches a ticker that is not in the snapshot (D-24), validates it and adds it as tier `on_demand`.

Request: `{}`. Response `200`:

```ts
{ asset: Asset; accepted: boolean; rejectedReason: I18nText | null; passport: DatasetPassport }
```

`accepted` is false when the listing currency is neither CAD nor USD, when fewer than 30 rows exist, or when validation fails (duplicate dates, non-positive prices). An accepted asset with fewer than 252 master observations carries the flag `short_history` (A-21). Errors: `503 upstream_unavailable` when the source cannot be reached. May take up to 20 s.

### 2.4 GET `/assets/{ticker}/attention` — P1

`200` → `{ signal: AttentionSignal; fact: Fact | null; evidence: Evidence | null; series: { date: ISODate; views: number }[] }`. When no page-view data exists, `signal.flag = "unknown"` and `series` is empty.

## 3. Profiles

### 3.1 GET `/profiles` — P0

`200` → `{ "items": Profile[] }`: the three defaults (with this session's threshold edits applied) followed by the session's custom profiles.

### 3.2 GET `/profiles/{profileId}` — P0

`200` → `Profile`. `404` when the custom profile belongs to another session.

### 3.3 POST `/profiles` — P1 (`profile_creator`)

Creates a custom profile from the creator form or from a confirmed agent draft.

```ts
// request
{
  name: string;                      // 1–40 chars
  age: number | null;
  riskLevel: RiskLevel;
  horizonYears: { min: number; max: number | null };
  objective: Objective;
  experience: Experience;
  reportingCurrency: Currency;
  preferences: Preferences;
  portfolio: { totalValue: number; positions: Position[] } | null;   // null → the server proposes a starting portfolio (optimizer §5)
  rules: PolicyRule[] | null;        // null → derived from the fields above (optimizer §3)
  fromDraftRunId: RunId | null;
}
// response 201
Profile
```

Validation: weights sum to 100 ± 0.01; every ticker exists in the universe; `horizonYears.min ≥ 0`; `max` null or ≥ `min`. Errors: `422 validation_error`.

### 3.4 PUT `/profiles/{profileId}` — P1

Body: same as 3.3 plus `version` (the version the client read). `409 conflict` on version mismatch. Default profiles cannot be replaced: `409 conflict`, message "default profiles are read-only; copy them instead".

### 3.5 DELETE `/profiles/{profileId}` — P1

`204`. Defaults: `409`.

### 3.6 PATCH `/profiles/{profileId}/rules/{ruleId}` — P0

Edits one rule (EF-11). Works on defaults too; the change is stored per session.

```ts
// request (at least one field)
{ threshold?: number; enabled?: boolean }
// response 200
{ rule: PolicyRule; profileVersion: number }
```

Effects: `origin` becomes `"user"`, `derivation` becomes null, `updatedAt` is set. Validation: `threshold` within `rule.bounds`; rules with `editable = false` (type `sim`) → `409 conflict`.

### 3.7 POST `/profiles/{profileId}/rules/derive` — P0

Recomputes every rule whose `origin` is `derived` from the profile's risk level, horizon and preferences (and resets user-edited thresholds when `reset = true`).

```ts
// request
{ reset: boolean; window?: WindowSpec }
// response 200
{ rules: PolicyRule[]; facts: Record<FactId, Fact>; profileVersion: number }
```

`facts` contains the derivation inputs (`budget.volatility`, `ref.sigma_single_stock_q3`, …) so the UI can show how each threshold was obtained.

### 3.8 PUT `/profiles/{profileId}/portfolio` — P1

Body: `{ totalValue: number; positions: Position[]; version: number }` → `200 Profile`. Defaults: stored per session, like rule edits.

### 3.9 GET `/profiles/{profileId}/overview` — P0

Everything the Home and Portfolio pages need that does not involve a model. Deterministic; cache key = profile version + data version + window.

Query: `window` (`full` default, `1y`, `3y`, `5y`, `ytd`).

```ts
// response 200
{
  profileId: ProfileId;
  asOf: ISODate;
  dataVersion: DataVersion;
  window: WindowSpec;
  snapshot: PortfolioSnapshot;                     // variant "before"
  returns: { ytdPct: number | null; y1Pct: number | null; y3Pct: number | null; y5Pct: number | null; factIds: Record<string, FactId> };
  risk: { volatilityPct: number | null; maxDrawdownPct: number | null; worst12mPct: number | null; stress2022Pct: number | null; riskCategory: RiskLevel; factIds: Record<string, FactId> };
  concentration: { hhi: number; effectiveN: number; topPositions: { ticker: Ticker; name: string; weightPct: number; marketValue: number; return1yPct: number | null; assetClass: AssetClass }[] };
  correlation: { tickers: Ticker[]; matrix: number[][] } | null;   // null when more than 20 positions
  ruleChecks: RuleCheck[];
  verdict: Verdict;
  counts: VerdictCounts;
  facts: Record<FactId, Fact>;
  limitations: LimitationCode[];
  holdingReturns?: { ticker: Ticker; return1yPct: number | null; return1yFactId: FactId | null }[];  // 1.6.0
}
```

`holdingReturns` (1.6.0, additive) has one entry per position with a positive weight, in the profile's holding order: the trailing 1-year return in the reporting currency (`return.period`, window `1y`, the same figure as `topPositions[].return1yPct`) and the fact that carries it. Both are `null` for a `CASH.*` position or when the history is too short. `topPositions` keeps only the five largest holdings. An API before 1.6.0 omits the key; clients then have a return for the top five only.

A return over a window longer than the available history is `null` (plan §5: "only show calculations supported by the available history"). `riskCategory` is the lowest risk level whose volatility budget (A-02) is at or above the measured volatility.

### 3.10 GET `/profiles/{profileId}/performance` — P0

Query: `window`, `benchmark` (optional ticker).

```ts
{ window: WindowSpec; currency: Currency; series: { date: ISODate; value: number }[]; benchmark: { ticker: Ticker; series: { date: ISODate; value: number }[] } | null; method: MethodId; limitations: LimitationCode[] }
```

`value` is an index starting at the portfolio's total value on the first date, computed with constant weights (`M_PORT_CONST_WEIGHTS`). The chart must show `LIM_CONSTANT_WEIGHTS`.

### 3.11 GET `/profiles/{profileId}/frontier` — P1 (`frontier_chart`)

Query: `window`, `universe` (`holdings` default | `asset_groups` | `holdings_plus:<ticker>`).

```ts
{
  window: WindowSpec; currency: Currency;
  assets: { ticker: Ticker; volPct: number; histReturnPct: number }[];
  minVarFrontier: { volPct: number; histReturnPct: number; weights: Position[] }[];   // M_FRONTIER_MINVAR
  histMvFrontier: { volPct: number; histReturnPct: number; weights: Position[] }[];   // M_FRONTIER_HIST_MV, illustration
  portfolio: { volPct: number; histReturnPct: number };
  portfolioAfter: { volPct: number; histReturnPct: number } | null;
  volBudgetPct: number;
  limitations: LimitationCode[];      // always includes LIM_PAST_NOT_FUTURE, LIM_MV_ILLUSTRATION, LIM_SAMPLE_WINDOW
  facts: Record<FactId, Fact>;

```

`histReturnPct` is the annualized historical return in the window, labelled "historical, in this sample" everywhere.

### 3.12 GET `/profiles/{profileId}/brief` — P0

Returns the latest succeeded `portfolio_brief` run for this profile version, data version and language (D-37).

Query: `lang`.

`200` → `{ run: Run | null; stale: boolean }`. `run` is null when none exists; the client then calls `POST /runs` with kind `portfolio_brief`. `stale` is true when, since the run, the profile version, the data version or the pinned data-manifest digest changed, or the brief was written under another runtime configuration: models (including a configured fallback model), Guardrail id or version, feature flags, run limits or data prefix. A redeploy that changes only the build revision does not make a brief stale.

### 3.13 POST `/profiles/{profileId}/strategies/simulate` — P1

Simulates one standing strategy (an automation the investor configures) on the history of today's holdings. Deterministic (`M_STRATEGY_SIM`), no model, nothing stored or executed: the browser keeps the investor's saved strategies (at most three per profile) as UI preferences. Session header required.

Request:

```ts
{
  strategy:
    | { kind: "rebalance"; trigger: "calendar" | "band"; frequency?: "monthly" | "quarterly" | "yearly"; bandPts?: number /* 1–25 */; costBps?: number /* 0–100 */ }
    | { kind: "contribute"; amount: number /* > 0, ≤ 1,000,000, reporting currency */; frequency: "monthly" | "quarterly"; allocation: "target" | "underweight"; costBps?: number }
    | { kind: "risk_guard"; triggerDrawdownPct: number /* 2–50 */; shiftPct: number /* 10–100 */; reentryDrawdownPct: number /* 0–50, below the trigger */; safeTicker?: Ticker | null; costBps?: number };
  window?: WindowSpec;   // default: the session window; custom ranges allowed
}
```

`rebalance` with `calendar` acts on the last master day of each period (`frequency`, default quarterly); with `band` it acts on a day when a position is more than `bandPts` (default 5) points from its target. Both restore today's weights. `contribute` adds `amount` on the first master day of each period: `target` splits it by today's weights, `underweight` sends it to the positions furthest below their target (never sells). `risk_guard` tracks the strategy's own peak: when the fall from that peak reaches `triggerDrawdownPct`, `shiftPct` % of each equity and crypto position moves to `safeTicker` (default: the largest bond fund held, else `CASH.<currency>`); once the fall is back under `reentryDrawdownPct`, today's weights are restored. Costs: `costBps` (default 0) × traded amount, taken from the portfolio.

Response:

```ts
{
  window: WindowSpec; currency: Currency; strategy: StrategyConfig;   // echoed with defaults filled in
  series: { date: ISODate; value: number }[];      // strategy, starting at today's total value
  baseline: { date: ISODate; value: number }[];    // the same holdings never touched (drift, no contributions)
  invested: { date: ISODate; value: number }[] | null;   // contribute only: starting value plus contributions
  metrics: StrategyMetrics; baselineMetrics: StrategyMetrics;
  actions: { date: ISODate; kind: "rebalance" | "contribute" | "de_risk" | "re_risk"; reason: I18nText; valueBefore: number;
             trades: { ticker: Ticker; amount: number /* signed */; weightBeforePct: number; weightAfterPct: number }[]; cost: number }[];
  actionsTruncated: boolean;                         // at most 200 actions, the latest kept
  plan: { monthsChecked: number; strategyMonthsInConflict: number; baselineMonthsInConflict: number;
          byRule: { ruleId: RuleId; code: string; strategyMonths: number; baselineMonths: number }[] };
  nextAction: { due: boolean; summary: I18nText; trades: StrategyTrade[] };
  method: "M_STRATEGY_SIM"; limitations: LimitationCode[];   // includes LIM_STRATEGY_COSTS, LIM_STRATEGY_EXECUTION, LIM_PAST_NOT_FUTURE, LIM_SIMULATION_ONLY
}
StrategyMetrics = { endValue: number; invested: number; gain: number; twrPct: number; volPct: number | null; maxDrawdownPct: number | null;
                    turnoverPct: number; costs: number; actions: number }
```

`twrPct`, `volPct` and `maxDrawdownPct` are time-weighted (contributions removed), so they compare with the baseline. `plan` checks the profile's enabled allocation rules (caps and floors on weights) on the holdings of each month end, for the strategy and the baseline; risk rules are not re-evaluated per month. `nextAction` describes what the strategy would do next from the last simulated day. Errors: `insufficient_data` (window without history), `validation_error`, `not_found`.

## 4. Request parsing and deterministic check

### 4.1 POST `/requests/parse` — P0

Turns free text into a structured request for the user to confirm (D-13). Uses the fast model once; no tools; never produces numbers that the user did not type.

```ts
// request
{ profileId: ProfileId; text: string /* 1–600 chars */; lang: Lang }
// response 200
ParsedRequest
```

Example:

```json
{
  "request": { "type": "move", "move": { "ticker": "TSLA", "sizePct": 25, "funding": { "mode": "auto" } } },
  "interpretation": { "en": "Add 25% of the portfolio to Tesla (TSLA); funding source to be compared.", "fr": "Ajouter 25 % du portefeuille à Tesla (TSLA) ; source de financement à comparer." },
  "confidence": "high",
  "missing": [],
  "warnings": [],
  "refused": null
}
```

Behaviour:

- "A quarter", "half", "25 percent" → `sizePct`. If no size is given for a move, `missing` contains `move.sizePct`.
- A theme without a specific asset → `type: "goal"` (when `goal_requests` is on; otherwise `missing` asks for a specific asset).
- "Buy it for me", "place the order" → `refused.reason = "trade_execution"`, `request = null`.
- "What should I buy?" with no goal → `refused.reason = "advice_request"` with a message offering to test a goal or a move instead.
- Unknown ticker → `warnings` says it will be fetched on demand, when that feature is on.

Errors: `503 upstream_unavailable` (model unavailable) — the client falls back to the manual form.

### 4.2 POST `/check` — P0

Deterministic evaluation of one move against a profile's rules. **No model call.** Used by the size slider, by threshold edits and by the compare view (EF-06, EF-07, EF-10, EF-11; acceptance CA-6).

```ts
// request
{
  profileId: ProfileId;
  move: ProposedMove | null;                 // null → check the current portfolio
  ruleOverrides?: { ruleId: RuleId; threshold?: number; enabled?: boolean }[];   // not persisted
  window?: WindowSpec;                       // default full
  asOf?: ISODate;                            // default data date; earlier dates go through the temporal gate
  compareFunding?: boolean;                  // default: true when move.funding.mode = "auto"
  knowledgeMode?: "current" | "historical" | null;   // "current" requires asOf = data date (else 422); an earlier asOf is always historical
}
// response 200
CheckResult
```

Example request and abridged response (values are `[CONTROL]` numbers from `contracts/controls.md` §7):

```json
{ "profileId": "robert", "move": { "ticker": "TSLA", "sizePct": 25, "funding": { "mode": "pro_rata" } } }
```

```json
{

```

Errors: `404 not_found` (profile or ticker), `422 insufficient_data` (ticker has no price on or before `asOf`), `422 validation_error` (`sizePct` ≤ 0 or > 100 − current weight for non-`new_money` funding; `from_holdings` without `fromTickers`).

Batch variant for the compare view: `POST /check/batch` with `{ items: CheckRequest[] }` (max 5) → `{ results: (CheckResult | ApiError)[]; differences?: RuleDifference[] }` — P0.

`differences` (1.6.0, additive) is present only when the batch has exactly two items and both are `CheckResult`s. It aligns the two results' `ruleChecks` by `ruleId` (rules SPEC §6, computed by code); A is the first item, B the second:

```ts
interface RuleDifference {
  ruleId: RuleId;
  reason: "threshold_differs" | "portfolio_differs" | "rule_only_in_a" | "rule_only_in_b" | "same";
  statusA: RuleStatus | null; statusB: RuleStatus | null;      // null on the side without the rule
  thresholdA: number | null; thresholdB: number | null;
  valueA: number | null; valueB: number | null;
}
```

`same` means equal status, threshold and value; otherwise `threshold_differs` when the thresholds differ, else `portfolio_differs`. An API before 1.6.0 omits the key; clients treat it as optional.

`CheckRequest` is the request shape above. `maxCompatibleSizePct` is a first-conflict grid boundary, not certification that every rule passes; preserve tension/nee disclosures. `counts` totals all returned statuses, including informational flag/simulation checks. The eight counted Robert checks in the control table are accompanied by three `info` checks.

## 5. Runs

### 5.1 POST `/runs` — P0

Starts an asynchronous run (D-06). Returns immediately.

```ts
// request — one of
{ kind: "decision";        profileId: ProfileId; lang: Lang; request: DecisionRequest; originalText?: string; window?: WindowSpec }
{ kind: "rebalance";       profileId: ProfileId; profileVersion: number; lang: Lang; positions: Position[] /* complete target, 1–40 */; window?: WindowSpec }
{ kind: "portfolio_brief"; profileId: ProfileId; lang: Lang; window?: WindowSpec; force?: boolean }
{ kind: "event_brief";     profileId: ProfileId; lang: Lang; eventId: EventId }
{ kind: "replay";          profileId: ProfileId; lang: Lang; request: DecisionRequest; asOf: ISODate; window?: WindowSpec }
{ kind: "profile_draft";   lang: Lang; text: string; fields?: Partial<Profile> }
// response 202
{ runId: RunId; status: "queued"; pollAfterMs: 1000 }
```

Rules:

- `portfolio_brief` without `force`: if a non-stale brief exists (3.12), the response is `200` with that run's `runId` and `status: "succeeded"`.
- `portfolio_brief`, with or without `force`: identical requests are de-duplicated on the server. Identical means the same session, profile and profile version, data version, data-manifest digest, brief runtime configuration (3.12; the build revision is not part of it), window and language. While an identical brief is queued or running, the response is `202` with that run's `runId`; if one succeeded less than 60 seconds ago, the response is `200` with its `runId` and `status: "succeeded"`. A failed or cancelled brief is never reused.
- `replay`: `asOf` must be one of the dates accepted by 7.1; otherwise `422 validation_error`.
- `rebalance`: the request is validated and compared exactly like `POST /rebalance/check` (see "Target allocation review" below) before the run is created: weights that do not sum to 100%, duplicate securities or an empty target → `422 validation_error`; an unsupported security → `404 not_found`; a `profileVersion` other than the current one → `409 conflict`. The run then reviews that deterministic comparison (steps in `run-events.md` §2.1); its result is `{ kind: "rebalance"; rebalance: ReviewedRebalance }` (`schemas.md` §9). No orders are placed or simulated.
- `event_brief`, `replay`, `profile_draft` return `501 feature_disabled` when their flags are off.
- A `decision` request of type `goal` returns `501` when `goal_requests` is off.

### 5.2 GET `/runs/{runId}` — P0

Query: `since` (optional step `seq`). `200` → `Run`. See `run-events.md` §3 for polling rules. `404` when the run belongs to another session.

### 5.3 GET `/runs` — P0

Query: `profileId`, `kind`, `limit` (default 20, max 100), `cursor`. `200` → `{ items: RunSummary[]; nextCursor: string | null }`.

```ts
interface RunSummary { runId: RunId; kind: RunKind; status: RunStatus; profileId: ProfileId | null; createdAt: ISODateTime; title: I18nText; verdict: Verdict | null; durationMs: number | null }
```

### 5.4 POST `/runs/{runId}/answers` — P1

Answers the clarifying question of a `waiting_input` run (D-16 d).

Request: `{ questionId: string; value: string }` → `202 { runId, status: "running" }`. `409 conflict` when the run is not waiting or the `questionId` does not match.

### 5.5 POST `/runs/{runId}/cancel` — P1

`200 { runId, status: "cancelled" }`. `409` when already finished.

### 5.6 GET `/runs/{runId}/facts/{factId}` — P0

`200` → `{ fact: Fact; inputs: Fact[]; usedBy: { sentenceIds: string[]; ruleIds: RuleId[] } }`. `inputs` are the facts this one was computed from (one level).

### 5.7 POST `/runs/{runId}/sabotage` — P1 (`sabotage_demo`)

Starts a `sabotage` run derived from a succeeded `decision` run (D-21). The parent run is never modified.

Request: `{ mode: SabotageMode /* default "invented_number" */; lang: Lang }` → `202 { runId, status: "queued", pollAfterMs: 1000 }`. The new run has `parentRunId` set and `flags.sabotage = mode`. Its result is a `SabotageResult`.

### 5.8 POST `/runs/{runId}/reveal` — P1 (`time_machine`)

For a succeeded `replay` run: returns what the scenarios did after the as-of date. Deterministic, no model.

Request: `{ until?: ISODate /* default: last date in the snapshot */ }` → `200 RevealResult`. `409 conflict` when the run is not a succeeded replay.

### 5.9 GET `/runs/{runId}/trace` — P1

Session-owned, read-only. Built only from what the worker recorded; nothing is re-executed and no provider or model text is added. `404 not_found` for another session's run. Response (JSON object, not a versioned contract type):

- `steps[]`: role, actor, status, timings, model, token usage, `modelCalls[]` (per physical attempt: model, outcome, provider error **code** only, `next` = `retry` | `repair` | `fallback`) and `toolCalls[]` (redacted errors).
- `budgets[]`: `{ name, used, limit }` for `llm_calls`, `research_calls`, `revisions`, `rewrites`, `scenarios`, `wall_clock_ms`.
- `events[]`: `resumed`, `step_reused_from_checkpoint`, `model_output_reused`, `model_retry`, `model_schema_repair`, `model_fallback`, `step_failed`, `run_failed`; `generation`, `claims`, `checkpoints`; `limitations[]`.
- `claimAudit[]`: per brief sentence, its status, failed audit codes and check families (`numeric`, `comparison`, `reference`, `policy`, `source_quote`, `source_interpretation`, `temporal`, `guardrail`, `structure`), and cited fact/evidence/rule IDs. `briefs[]` adds global checks and whether the signed ledger hash matches the restored checkpoint.
- `sources[]`: up to 12 evidence items with the SHA-256 of the full captured source, Unicode-character excerpt/quote offsets and excerpts (untrusted data), or `unavailable` when no verified same-run capture exists.

A model fallback happens only when `APLOMB_BEDROCK_FALLBACK_MODEL_ID` names a different supported Bedrock model; it is charged against `llm_calls` and recorded here.

### Global profile and analytics additions (1.2.0)

Create/replace profile requests accept optional `investorContext`: country code (two uppercase
letters), investorType, language, up to 20 objectives (name, horizonYears > 0, priority 1–100,
optional targetAmount in reporting currency, optional deadline, and origin), liquidityNotes and
riskCapacityNotes. These are user statements, not regulatory policies or verified financial
facts. Existing profiles require no migration. Reporting coverage is advertised by `Meta.reportingCurrencies`; country context does not establish tax coverage.

`GET /assets/{ticker}/analytics` accepts the same preset/custom window semantics as portfolio
reads and a supported ISO reporting `currency`. It returns AssetAnalyticsResponse with four measurements and a
local claims ledger. Missing history returns null values with reasons, never zero risk.

`GET /profiles/{profileId}/risk` returns RiskDiagnosticsResponse with daily historical 95% VaR,
ES, signed variance contributions and their local facts. Tail estimates require 100 returns;
shares are undefined for zero variance. These analytics do not automatically change policy.

Account creation requires explicit portfolio/value, name and expected profile version; the
original portfolio becomes the Primary account on first creation. At most 20 accounts and 40
positions per analyzed portfolio are supported. Selection preserves unsaved-in-account active
holdings and increments the profile version. `accountId=aggregate` combines value-weighted
positions in the common reporting currency, deduplicates securities and prohibits holdings
edits. Optional creation `currency` identifies the native currency of the explicitly entered capital (default: profile reporting currency). Supported conversion uses the pinned FX snapshot at `dataAsOf`, via CAD-per-unit cross rates; missing quotes reject creation without changing state.

`PortfolioAccount.nativeValuation` retains the original capital/currency, reporting value, conversion rate, snapshot and valuation date, source rows/passports and independently executed check codes. Account portfolios remain stored in reporting currency so individual and aggregate analyses share one base. These are fixed fictional capital inputs, not current asset valuations, currency trades, forecasts or transfer instructions. No spread, fees or taxes are inferred. Switching accounts does not silently revalue native capital. Editing capital explicitly in reporting currency clears the earlier native receipt. Holdings-only edits preserve it. Snapshot/version, source row identity, quote set, currency direction and multiplication are checked independently against the pinned dataset. Dates and rate inputs remain inspectable.
All account operations require session ownership, optimistic version and profile_creator.

### Target allocation review

| Method and path | Purpose | Response |

| POST `/rebalance/check` | Full target allocation, including reductions and removals | `RebalanceResponse` |

`RebalanceRequest` contains `profileId`, the current `profileVersion`, the complete target `positions` and optional `window`.
